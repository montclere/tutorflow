# ADR — Платформа и рабочий процесс

## WEB

- WEB-1 [готово] Интерфейс проводит репетитора от регистрации через профиль и включение кабинета до выпуска ссылки. Получатель видит назначение, подтверждает один контакт либо входит и явно принимает приглашение. Списки и детали показывают только данные, возвращённые сервером для выбранного кабинета.
- WEB-2 [готово] Ссылка на приглашение переносит секрет во фрагменте URL. Приём и отзыв подтверждает сервер. После принятия интерфейс открывает доступную карточку без секрета в адресе.

## INF-1–5 — стек, границы и локальная проверка

Репозиторий использует отдельные worktree от dev, ручное ревью и выпуск из main. Историческое описание продукта перенесено из develop и сохранено отдельно. [Процесс](../workflow.md) · [Описание продукта](../spec.md)

Backend — модульный монолит Python. FastAPI и Uvicorn обслуживают HTTP/OpenAPI, SQLAlchemy async с psycopg работает с PostgreSQL, Alembic управляет схемой. PostgreSQL выбран ради транзакций, блокировок и ограничений, которые проверяются на настоящей БД. uv фиксирует зависимости. Ruff, Pyright и pytest поддерживают локальные проверки и границы импортов. Argon2id используется через argon2-cffi, email синтаксически проверяет email-validator, API-тесты используют httpx2 через Starlette.

Браузер использует React на Vite ([INF-7](#inf-7--стек-веб-интерфейса)). Caddy отдаёт собранный фронтенд и проксирует API на одном origin. Playwright проверяет реальные сессии Chromium. Из соседнего форума перенесён общий Compose с оверрайдами, отдельный шаг миграции и единая команда проверки. GitHub Actions и обязательные хуки не участвуют в процессе. Хранилище файлов, ClamAV и серверные скрипты форума не нужны этому сценарию.

Dev и тесты используют Mailpit и закрытый SMS inbox. Mailpit уже доступен в локальной инфраструктуре, покрывает реальный SMTP без внешнего сервиса и не входит в prod. В prod отдельная БД, версионированные образы, HTTPS и штатные транспорты. [Mailpit runtime](https://mailpit.axllent.org/docs/configuration/runtime-options/) · [Запуск](../../deploy/README.md)

## INF-7 — стек веб-интерфейса

- INF-7 [готово] Интерфейс — Vite + React 19 + TypeScript. Лендинг стилизован CSS Modules и токенами `frontend/src/styles/tokens.css`, кабинет — компонентами shadcn/ui на Tailwind v4 (слои `theme` и `utilities` без preflight, тема — алиасы на те же токены) и иконками `lucide-react`. Маршрутизатор — минимальный на History API (`frontend/src/app/router.ts`). Тесты логики — Vitest, линтер — ESLint 9 с typescript-eslint, react-hooks и jsx-a11y; браузерные сценарии — Playwright на стеке `./scripts/dev.sh check`.
- INF-7.1 [готово] Сборка кладёт статику в `frontend/dist` с файлами в `/assets/*` — так её отдаёт Caddy (`deploy/web.Dockerfile`). Шрифты лежат в сборке, а не на Google Fonts: CSP разрешает только свой origin.
- INF-7.2 [готово] Обращения к API идут через один клиент `frontend/src/shared/api/client.ts` по договору [API](../api/README.md): cookie-сессия, `X-CSRF-Token`, ошибки Problem Details по `code`. Модули ресурсов (`features/auth/api`, `cabinet/api`) переводят ответы в поля интерфейса и сами `fetch` не вызывают. Тестовые данные кабинета включаются только флагом `VITE_DEMO=1` и в рабочей сборке не подменяют ответы сервера.

Почему React, а не статический TypeScript: интерфейс к моменту объединения веток уже содержал лендинг, мастер регистрации и кабинет с расписанием, учениками, заданиями и финансами на компонентах shadcn/ui; перенос этого на шаблоны без фреймворка повторил бы работу без выгоды для пользователя. Цена — зависимости фронтенда и шаг сборки Vite в `dev.sh`; CSP и схема отдачи Caddy не меняются. Решение принято владельцем интерфейса и ждёт ревью второго участника.

## INF-6 — публичные HTTP-ответы

- INF-6 [готово] Сохраняем один формат Problem Details и стабильные коды. `type` обозначает тип проблемы, `instance` — конкретный запрос, `request_id` совпадает с `X-Request-ID`. Человекочитаемые сообщения берутся из каталога без входных значений. OpenAPI использует ту же схему и каталог.
- INF-6.1 [готово] Ошибка синтаксиса JSON — 400, неподдерживаемый тип переданного тела на JSON-маршруте — 415, корректный JSON с неправильной структурой — 422. Неизвестный путь — 404, другой метод на известном ресурсе — 405 с полным `Allow`. Лимит — 429 с округлённым вверх временем `Retry-After`. Отказ соединения с БД — 503, непредвиденный сбой — 500.
- INF-6.2 [готово] Для неподтверждённой сессии, неверного входа и отказа CSRF API отвечает 403 с разными стабильными кодами. Cookie-сессия и вход по JSON не используют HTTP challenge, а RFC 9110 требует challenge у 401. Для валидного запроса входа отказ одинаков для неизвестного логина и неверного пароля. У закрытых объектов сохраняется 404. Повторы создания сохраняют 200, первичное создание — 201. Ответ 204 пустой.


Из соседнего форума взяты стабильный `code`, общий Problem Details и полный `Allow`. Для TutorFlow идентификатор ошибки строится из ID запроса, а публичный текст не берётся из исключений и валидатора. Это исключает отражение пути с чужим ID, данных формы и внутренних ошибок. Клиенты должны учитывать замену 401 на 403 при отказе cookie-аутентификации и входа. Машинные коды этих отказов сохранены. Зафиксирована разница между сбоем БД и ошибкой её использования.

Источники: [RFC 9110, семантика HTTP](https://www.rfc-editor.org/rfc/rfc9110.html), [RFC 9457, Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html), [RFC 6585, §4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4), [OWASP Error Handling](https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html), [OWASP Authentication, ответы входа](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages).
