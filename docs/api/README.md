# api

Первый HTTP API TutorFlow. Базовый путь `/api/v1`. Правила, причины и статусы собраны в [ADR](../adr/README.md).

- [Identity](identity.md) — аккаунт, личный профиль, включение кабинета преподавателя, сессии и граница договора входа.
- [Students](students.md) — карточки, приглашения, связи и представления кабинетов.
- [Lessons](lessons.md) — занятия, еженедельные серии, переносы и расписание.
- `GET /health` — 200 `{"status":"ok"}` при доступности процесса. Это не проверка БД.

## Общий договор

- Тело JSON отправляется с `Content-Type: application/json` или `application/*+json`. Неизвестные поля запрещены. UUID передаются строкой, время — RFC 3339 UTC. Владелец определяется сервером.
- Ответы приложения содержат `Cache-Control: no-store` и сформированный сервером `X-Request-ID`. Секреты и контакты не передаются в пути или query API, не записываются в журналы и ошибки.
- API использует cookie и CSRF. Любой POST/PATCH/PUT/DELETE требует cookie context и `X-CSRF-Token`. Для CLI сначала `GET /auth/csrf` с cookie jar. До входа возможны выдача CSRF, маршруты регистрации, входа, восстановления, предпросмотр приглашения и проверка процесса; прочие описанные маршруты требуют активного подтверждённого аккаунта.
- Списки: `limit` от 1 до 100, по умолчанию 20; `cursor` подписан и привязан к актору, фильтру и сортировке. Результат `{items, next_cursor}`, без общего числа чужих объектов. Порядок — по `created_at DESC` и ID DESC; карточки по `updated_at DESC, student_card_id DESC`. В преподавательском списке `status=active` по умолчанию, `status=archived` — свой архив.
- `expected_version` передаётся только там, где указан в таблицах маршрутов; это целое >= 1. При устаревшей версии — 409 без записи. Для принятия и отзыва ссылки используется проверка её текущего состояния под блокировкой; см. [повторы](students.md#принятие-и-повтор).
- URL маршрутов имеют точную форму без завершающего слеша. При первом создании 201 содержит относительный `Location` созданного ресурса. Документированный повтор даёт 200. Ответ 204 имеет пустое тело.

## Ошибки

Приложение возвращает `application/problem+json` по RFC 9457. `type` содержит стабильный URI типа ошибки `urn:tutorflow:problem:<code>`. Клиент может ветвиться по `code`. `title` и `detail` предназначены для человека. `status` совпадает с HTTP-статусом. `instance` — `urn:uuid:<request_id>`, идентификатор конкретного ответа. `request_id` совпадает с заголовком `X-Request-ID`. Для 422 возможен список `errors: [{field, code}]` с кодами `required`, `invalid_value`, `unknown_field`. Имена незнакомых полей и исходные значения не возвращаются.

| HTTP | Когда |
| --- | --- |
| 400 | Нарушен синтаксис запроса, либо код подтверждения или приглашение недоступны |
| 403 | Сессия отсутствует или недействительна, вход отклонён, CSRF не прошёл либо действие запрещено |
| 404 | Маршрут или объект отсутствует либо объект недоступен актору |
| 405 | Метод не поддерживается. Допустимые методы перечислены в `Allow` |
| 409 | Конфликт состояния или версии при допустимом действии |
| 413 | Тело изменяющего запроса больше 16 КиБ |
| 415 | Переданное тело на маршруте с JSON-схемой имеет неподдерживаемый тип |
| 422 | Запрос разобран, но значения, структура, ID или курсор недопустимы |
| 429 | Достигнут лимит. `Retry-After` содержит целое число секунд до следующей попытки |
| 500 | Непредвиденная внутренняя ошибка |
| 503 | Зависимость временно недоступна |

Конкретные коды операций перечислены в `x-problem-codes` в `/openapi.json` backend. Общие 404 и 405 применяются при маршрутизации. Для 401 потребовался бы настоящий HTTP challenge, поэтому текущий вход по JSON и серверная cookie-сессия используют 403. Клиент различает необходимость входа и отказ прав по `code`. При недоступности самого приложения ответ может сформировать прокси вне этого договора. Браузер показывает безопасное резервное сообщение и не повторяет изменяющие запросы автоматически.
