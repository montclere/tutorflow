# Стартовый промпт для Codex — установка репозитория TutorFlow

Выполни настройку **в текущем чистом репозитории**. Считай файлы, уже находящиеся в корне, утверждённой стартовой структурой.

## Цель
Подготовь лёгкий, расширяемый монорепозиторий модульного монолита TutorFlow с автоматизируемым циклом `BR → GitHub Issue → адресный тест → реализация → PR → CI → merge`.

## Последовательность (не пропускай шаги)
1. Прочитай `AGENTS.md`, `docs/product.md`, схемы `docs/use-cases.md`, `docs/business-rules.md`, три SKILL.md и только нужные файлы scripts. Не выдумывай новые бизнес-требования.
2. Проверь окружение (`git`, `gh`, Codex, выбранные менеджеры пакетов). Не выводи токены и секреты. Проверь `gh auth status`, доступ к репозиторию и его приватность. Если авторизация отсутствует, выполни остальную локальную настройку и сообщи точный блокер.
3. Предложи владельцу **только решения, существенно влияющие на проект**: язык и framework backend, frontend, БД, стратегия миграций и тестов, способ auth. Если стек уже утверждён, не переспрашивай. Не выбирай стек самовольно без возможности согласования.
4. Создай минимальные `backend/` и `frontend/` только после выбора стека. Архитектура — модульный монолит: Identity, Students, Scheduling как отдельные доменные модули внутри одного backend-приложения; общая инфраструктура минимальна. Не создавай микросервисы, event bus, DDD-слои, кучу пустых абстракций, Docker/Kubernetes/queues без текущей потребности.
5. Назначь **одну воспроизводимую команду** для установки зависимостей и lockfiles. Настрой локальные unit/integration/contract tests и статическую проверку (lint/typecheck) средствами выбранного стека. Выбери целевой механизм запуска по BR-ID (например `pytest -m br_005` или эквивалент framework), настрой `scripts/checks.json`, `backend/tests/rule-map.json`; проверь, что `python scripts/check.py rule BR-...` действительно запускает только заявленные тесты и НЕ проходит, если они отсутствуют.
6. Настрой `.github/workflows/ci.yml`: установку зависимостей по lockfile и кешированию; PR и main; `python scripts/check.py ci`. CI должен реально включать full suite и статические проверки. Для зависимости от DB запусти сервис БД в CI только если интеграционные тесты её используют. Не отключай full suite ради ускорения. Не делай третий избыточный workflow.
7. GitHub: если есть доступ, создай labels `type:implementation`, `blocked`, `priority:high`, `area:identity`, `area:students`, `area:scheduling`. Создай Project с колонками Backlog/Ready/In Progress/Review/Done если текущие возможности gh/API позволяют; иначе выдай конкретные ручные действия. Установи защиту main: PR перед merge + обязательный `verify` check, если тариф/права позволяют. Не включай автослияние и не делай репозиторий публичным.
8. Pre-commit: настрой быстрые проверки в `.pre-commit-config.yaml`. Полный набор проверок запускается отдельно.
9. Проверь `python scripts/check.py spec`, `python scripts/check.py pr`, `python scripts/check.py ci` локально. Для CI учти, что workflow в GitHub не мог выполниться до push/PR; не утверждай обратного.
10. Создай небольшой initial commit и PR по согласованию. Не коммить секреты. Merge и закрытие Issues только после реального успешного CI и разрешения владельца.

## Ограничения расхода токенов и времени
- При работе над Issue читай лишь упомянутые BR и связанные UC; планируй тестовые случаи коротко.
- Один RED для новых адресных тестов, затем код и один GREEN; повторные прогоны только на провале.
- `scripts/check.py pr` локально один раз перед PR; full suite в CI. Логи успешных проверок — краткие, подробности в .artifacts.
- Делай одно итоговое review, не серию AI-ревью после каждого файла.
- Любые дополнительные инструменты/боты/хуки добавляй только после обоснования пользы и издержек. Не запускай автономный бесконечный цикл.

## Первые работы
После настройки запусти `plan-issues` только для BR-001, BR-005, BR-029 (и реальных обязательных зависимостей) с целью: **преподаватель регистрируется, создаёт карточку ученика без аккаунта и назначает индивидуальный урок**. Сначала получи небольшие готовые issues с зависимостями; не пытайся реализовать все 75 правил за один PR.

## Отчёт результата
Кратко перечисли: утверждённый стек; созданные ключевые пути; что реально прошло локально; что реально прошло в GitHub CI; ссылки на Issues/Project/PR; что заблокировано; следующую единственную конкретную задачу. Не создавай отдельные implementation-plan.md, decisions.md, progress.md.
