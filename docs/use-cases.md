# TutorFlow — MVP Use Cases

Версия: draft-1 · 2026-11-24. Основа: обсуждение владельца продукта; не является описанием реализованного ПО.

## Формат

Адаптированный *casual use case* А. Кокберна: **цель → акторы → предпосылки → основной поток → варианты → результат → требования → гипотеза ценности**. Use Case описывает пользовательскую цель, не API и не таблицы. В каждой секции отмечено, где поведение согласовано и где ещё требует точности. Проверяемые правила вынесены в `business-rules.md`, чтобы не дублировать их текст.

**Классы:** `С` — согласовано как концепция; `Д` — деталь ещё должна быть определена перед реализацией. Гипотезы отличий от конкурентов не считаются доказанными.

## UC-001 — Преподаватель начинает работу

- **Актор:** преподаватель.
- **Цель:** начать работу без обязательного мастера настройки.
- **Предусловие:** преподаватель получает доступ к регистрации.
- **Основной поток:** 1) регистрируется; 2) получает рабочее пространство; 3) видит кабинет с доступной настройкой профиля; 4) при желании сохраняет часовой пояс и добавляет личный блок в календарь.
- **Варианты:** необязательная первоначальная настройка; настройку можно пропустить или выполнить позже. Кабинет остаётся доступным без профиля и календарных блоков.
- **Результат:** кабинет доступен, можно начать работу без заполнения расширенного профиля.
- **Требования:** BR-001–BR-004.
- **Гипотеза ценности:** короткий путь от регистрации до первой полезной операции.
- **Статус:** С.

## UC-002 — Преподаватель добавляет или приглашает ученика

- **Акторы:** преподаватель, ученик.
- **Цель:** начать учитывать занятия ученика и при необходимости дать ему доступ.
- **Предусловие:** преподаватель вошёл в своё пространство.
- **Основной поток:** 1) преподаватель создаёт карточку или приглашение; 2) при необходимости заранее задаёт персональные учебные параметры; 3) работает с карточкой без регистрации ученика; 4) отправляет приглашение; 5) ученик входит в существующий аккаунт либо регистрируется; 6) подтверждённая связь соединяет аккаунт с карточкой; 7) ученик видит разрешённые ранее созданные данные.
- **Варианты:** приглашение отменено и выпущено повторно; пользователь уже занимается у другого преподавателя — новый преподаватель получает независимую карточку; преподаватель может продолжать без подключения ученика. Импорт таблиц не входит в текущий объём.
- **Результат:** одна карточка в пространстве преподавателя; аккаунт ученика необязателен.
- **Требования:** BR-005–BR-012.
- **Гипотеза ценности:** преподаватель не ждёт регистрации учеников, а подключение происходит постепенно.
- **Статус:** С; детали безопасной привязки — Д.

## UC-003 — Преподаватель подключает взрослого

- **Акторы:** преподаватель, взрослый, при необходимости ребёнок.
- **Цель:** предоставить взрослому доступ к определённому ученику у конкретного преподавателя.
- **Предусловие:** в пространстве преподавателя существует карточка ученика.
- **Основной поток:** 1) преподаватель открывает карточку; 2) создаёт приглашение взрослому; 3) взрослый видит назначение приглашения и входит/регистрируется; 4) после принятия получает кабинет с разрешёнными сведениями об ученике; 5) получает доступ только к данному преподавателю, а не к другим занятиям ребёнка.
- **Варианты:** взрослый получает приглашения к нескольким ученикам; права из готового профиля (наблюдатель, плательщик, представитель — названия предварительные) с настройками; если у ребёнка нет собственного доступа, взрослый, приглашённый для его подключения, может создать детский вход и управлять им. Простой наблюдатель не управляет входом ребёнка.
- **Результат:** учебное разрешение для данного преподавателя; отдельная глобальная семейная связь не возникает.
- **Требования:** BR-013–BR-020.
- **Гипотеза ценности:** единый кабинет взрослого при независимом доступе к разным преподавателям.
- **Статус:** частично С; модель детского входа, передачи управления и согласия — Д, блокирует запуск детского входа в production.

## UC-004 — Преподаватель управляет группой

- **Актор:** преподаватель.
- **Цель:** организовывать совместные действия с несколькими учениками, сохраняя индивидуальный учёт.
- **Основной поток:** 1) создаёт группу, в том числе пустую; 2) добавляет учеников; 3) назначает группе занятие, материал, задание или сообщение; 4) управляет отдельными участниками и результатами.
- **Варианты:** ученик состоит в нескольких группах; новый участник получает доступ к прошлой истории по настройке; состав конкретного занятия может отличаться от состава группы; группа архивируется.
- **Результат:** групповые операции доступны, личные карточки не сливаются.
- **Требования:** BR-021–BR-027.
- **Гипотеза ценности:** одна групповая операция вместо ручного повторения, без потери персонализации.
- **Статус:** С; история доступа и финансовые последствия изменений группы — Д.

## UC-005 — Преподаватель создаёт и согласовывает занятие

- **Акторы:** преподаватель; по необходимости ученик или уполномоченный взрослый.
- **Цель:** быстро назначить индивидуальное или групповое занятие.
- **Основной поток:** 1) преподаватель нажимает интервал календаря или «Создать занятие»; 2) выбирает участника/группу, дату и продолжительность; 3) система предлагает значения по умолчанию; 4) преподаватель создаёт занятие непосредственно или отправляет предложение; 5) событие отражается в доступных участникам календарях.
- **Варианты:** несколько учеников без постоянной группы; незарегистрированный ученик; подтверждение/отклонение предложения; предупреждение о пересечении без раскрытия чужих данных; личная занятость — календарный блок, не урок.
- **Результат:** сохранённое занятие или предложение со статусом.
- **Требования:** BR-028–BR-036.
- **Гипотеза ценности:** минимум шагов и согласование времени внутри платформы.
- **Статус:** С; параметры подтверждения — Д.

## UC-006 — Преподаватель задаёт регулярное расписание

- **Актор:** преподаватель.
- **Цель:** назначить серию занятий и управлять исключениями.
- **Основной поток:** 1) превращает урок в повторяющийся или настраивает несколько дней; 2) выбирает бессрочное/до даты/по числу повторений; 3) при необходимости ставит паузу, каникулы или исключения.
- **Варианты:** изменение одного события, будущих событий или серии; редактирование участников конкретного группового урока; временные исключения и отсутствие преподавателя.
- **Результат:** повторяемый план, отдельные занятия допускают индивидуальные изменения.
- **Требования:** BR-037–BR-043.
- **Гипотеза ценности:** гибкие регулярные занятия без ручного пересоздания.
- **Статус:** С; значение «вся серия» относительно прошедших уроков — Д.

## UC-007 — Участники переносят или отменяют занятие

- **Акторы:** преподаватель; ученик или взрослый с правом управлять записью.
- **Цель:** изменить встречу без потери связанных данных.
- **Основной поток:** 1) преподаватель редактирует урок либо перетаскивает его; или участник отправляет запрос; 2) система предупреждает о конфликтах; 3) после принятого изменения обновляет план, историю, будущие напоминания и передаёт факты для финансового учёта.
- **Варианты:** отмена с полным, частичным, нулевым начислением или ручным решением; изменение группы целиком или отдельного участия; несколько переносов через обычное перемещение событий вместо специальной команды «обмен».
- **Результат:** понятное актуальное расписание с историей и обновлёнными связанными последствиями.
- **Требования:** BR-044–BR-052.
- **Гипотеза ценности:** одно изменение — согласованное обновление связанных процессов.
- **Статус:** С; финансовые формулы и блокировка предлагаемых слотов — Д.

## UC-008 — Преподаватель проводит и завершает занятие

- **Акторы:** преподаватель, участники урока.
- **Цель:** зафиксировать факт и результаты урока с минимумом действий.
- **Основной поток:** 1) урок наступает; 2) преподаватель отмечает результат занятия и индивидуальную посещаемость; 3) завершает занятие через короткий сценарий; 4) система выполняет настроенные связанные действия или предлагает их подтвердить.
- **Варианты:** напоминание после времени окончания; необязательное автоматическое закрытие по правилам; ученик может отметить собственное участие; у группового урока индивидуальная посещаемость и стоимость; AI может подготовить черновик домашнего задания или отчёта, но не подтверждать автоматически факт проведения.
- **Результат:** факт проведения и состояние последующей обработки различимы, последствия прослеживаются.
- **Требования:** BR-053–BR-061.
- **Гипотеза ценности:** «закрыть урок» одной короткой операцией вместо длинного списка ручных действий.
- **Статус:** С; окончательные статусы и автоматические финансовые действия — Д.

## UC-009 — Преподаватель открывает время для записи

- **Акторы:** преподаватель, ученик, взрослый с правом управления записью.
- **Цель:** согласовать урок через доступные интервалы без переписки.
- **Основной поток:** 1) преподаватель выделяет интервал календаря либо задаёт регулярную доступность; 2) указывает аудиторию и режим — немедленная запись либо запрос; 3) ученик/уполномоченный взрослый выбирает время; 4) система фиксирует запись или резервирует время для решения преподавателя; 5) доступность оставшегося интервала пересчитывается.
- **Варианты:** предложение нескольких вариантов с выбором одного; ученик указывает собственную доступность или недоступность; система подсказывает пересечения интервалов, не назначая занятие сама; интервалы допускают несколько последовательных занятий с настраиваемыми перерывами.
- **Результат:** запись или запрос на запись, опубликованная доступность актуализирована.
- **Требования:** BR-062–BR-070.
- **Гипотеза ценности:** самостоятельная запись при контроле преподавателя и без удаления длинного доступного интервала целиком.
- **Статус:** С; точный алгоритм резерва, продолжительности и конфликта — Д.
