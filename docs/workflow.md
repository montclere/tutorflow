# workflow

Работа двух людей, каждый со своим агентом.

## Один раз

1. Выдать второму участнику доступ Write к репозиторию.
2. Из чистой main создать dev и опубликовать: `git switch -c dev`, `git push -u origin dev`. Если dev уже есть — использовать её.
3. В настройках GitHub защитить main и dev: PR, одно одобрение второго участника, запрет force push. Проверки запускать локально через `./scripts/dev.sh check`, результат указывать в PR. После первого запуска Actions добавить обязательную проверку `check` для dev.
4. Main предназначена для выпусков; пока приложения нет, она содержит исходный каркас. Dev — общая интеграция. Задачи идут в dev, выпуск — PR dev → main.
5. Вместе заполнить [spec](spec.md) и выбрать стек в [decisions](decisions.md).

## Автоматические проверки

- GitHub Actions запускает `./scripts/dev.sh check` при push в main и открытии, обновлении или повторном открытии PR в dev; также доступен ручной запуск.
- Push в main проверяется после записи коммита; обязательный `check` в правилах dev блокирует слияние PR до успеха.
- CI проверяет каркас и все подключённые модули. Пока модуль содержит только документацию, допускается SKIP; появление кода или конфигурации без `scripts/check.sh` считается ошибкой.
- Вместе с первым кодом подключить установку зависимостей и нужные сервисы в workflow, а линт, типы, тесты и сборку — в проверку модуля.

## Каждая задача

1. Создать GitHub Issue по шаблону либо файл из [шаблона](tasks/template.md). Указать исполнителя, ревьюера, результат, файлы, критерии и ID правил.
2. До параллельной работы согласовать [API](frontend-api.md) и общие файлы. Одна задача — один исполнитель; второй участник делает другую задачу или ревью.
3. Взять свежую dev и создать отдельный worktree. Пример из корня репозитория:

```bash
git fetch origin
git worktree add -b feat/person-a/task-name ../tutorflow-person-a-task origin/dev
cd ../tutorflow-person-a-task
```

4. Запустить агента в этом worktree; дать задачу по примеру ниже. Второй участник использует другую ветку, например `feat/person-b/other-task`, и свой каталог.
5. Агент читает AGENTS.md, меняет правила, тесты и код, запускает `./scripts/dev.sh check`, обновляет документы и передаёт результат человеку.
6. По поручению человека агент делает commit/push и PR в dev. Формат: `feat(backend): добавлен ...`, `fix(frontend): исправлен ...`, `docs(repo): описан ...`.
7. Второй участник проверяет diff, критерии и результат проверок; его агент может провести отдельное ревью. Автор исправляет замечания.
8. После успешных локальных проверок, зелёного `check` в PR и одобрения слить PR в dev, закрыть задачу. Если файлы устарели — влить свежую origin/dev в свою ветку, разрешить конфликты и повторить затронутые проверки.

## Если пересеклись

- Общие файлы: behavior, decisions, frontend-api, stages, корневые настройки и зависимости.
- Заранее договориться, кто меняет контракт; второму участнику дать ссылку на задачу/PR.
- Новые ID правил сверять со свежей dev; столкнувшиеся новые ID развести до слияния вместе с их ссылками.
- Не редактировать рабочий каталог другого участника, не перетирать его правки и не переписывать общие ветки.
- При конфликте сравнить смысл обеих правок; не принимать целиком ours/theirs без проверки.

## Задание агенту

```text
Задача: <ссылка или описание>.
Прочитай AGENTS.md и локальные правила. Результат: <наблюдаемое поведение>.
Область: <папки>. Критерии: <что проверить>. Связанная задача второго участника: <ссылка>.
Работай в текущем worktree. Выполни проверки, обнови документы и передай результат на ревью.
```

## Передача на ревью

- Что сделано и зачем, задача и ID правил.
- Проверки: команды, результат, пропуски.
- Изменения контракта, миграции, переменные окружения.
- Оставшиеся ограничения и следующий шаг второго участника.

## Выпуск

- Только по поручению владельца и по [release](skills/release.md).
- Пока серверов и приложения нет, релиз и деплой не выполняются.
