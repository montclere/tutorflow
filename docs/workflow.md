# workflow

Работа двух людей, каждый со своим агентом.

## Один раз

1. Выдать второму участнику доступ Write к репозиторию.
2. Из чистой main создать dev и опубликовать: `git switch -c dev`, `git push -u origin dev`. Если dev уже есть — использовать её.
3. В настройках GitHub защитить main и dev: PR, одно одобрение второго участника, запрет force push. Проверки запускать локально через `./scripts/dev.sh check`, результат указывать в PR. Если старая проверка `check` была обязательной в правилах GitHub, убери требование к этому статусу при переходе на локальные проверки.
4. Main предназначена для выпусков; сейчас в ней только начальный коммит. Dev — общая интеграция. Задачи идут в dev, выпуск — PR dev → main.
5. Выбрать первый сценарий из [spec](spec.md), стек и границы MVP в [ADR платформы](adr/platform.md). Выполнить `./scripts/dev.sh setup`.

## Локальные проверки

- После первого получения проекта выполни `./scripts/dev.sh setup`. Перед push, созданием и обновлением PR выполни `./scripts/dev.sh check` и приложи результат к PR.
- Проверка поднимает отдельные PostgreSQL, backend и web для тестов, прогоняет backend, сборку, браузерные сценарии и проверяет Compose. Инструкции находятся в [scripts](../scripts/README.md).
- Локальный результат и ревью второго участника обязательны. GitHub Actions и обязательный статус от workflow в этом процессе не используются.

## Каждая задача

1. Создать GitHub Issue по шаблону либо файл из [шаблона](tasks/template.md). Указать исполнителя, ревьюера, результат, файлы, критерии и ID правил.
2. До параллельной работы согласовать [API](api/README.md) и общие файлы. Одна задача — один исполнитель; второй участник делает другую задачу или ревью.
3. Взять свежую dev и создать отдельный worktree. Пример из корня репозитория:

```bash
git fetch origin
git worktree add -b feat/task-name ../tutorflow-task-name origin/dev
cd ../tutorflow-task-name
```

4. Запустить агента в этом worktree; дать задачу по примеру ниже. Второй участник использует другую ветку, например `feat/other-task`, и свой каталог.
5. Агент читает AGENTS.md, меняет правила, тесты и код, запускает `./scripts/dev.sh check`, обновляет документы и передаёт результат человеку.
6. По поручению человека агент делает commit/push и PR в dev. Формат: `feat(backend): добавлен ...`, `fix(frontend): исправлен ...`, `docs(repo): описан ...`.
7. Второй участник проверяет diff, критерии и результат проверок; его агент может провести отдельное ревью. Автор исправляет замечания.
8. После успешных локальных проверок, записи результата в PR и одобрения слить PR в dev, закрыть задачу. Если файлы устарели — влить свежую origin/dev в свою ветку, разрешить конфликты и повторить затронутые проверки.

## Если пересеклись

- Общие файлы: ADR, API, stages, корневые настройки и зависимости.
- Заранее договориться, кто меняет контракт; второму участнику дать ссылку на задачу/PR.
- Новые ID правил сверять со свежей dev; столкнувшиеся новые ID развести до слияния вместе с их ссылками.
- Не редактировать рабочий каталог другого участника, не перетирать его правки и не переписывать общие ветки.
- При конфликте сравнить смысл обеих правок; не принимать целиком ours/theirs без проверки.

## Задание агенту

```text
Задача: <ссылка или описание>.
Прочитай AGENTS.md и локальные правила. Результат: <наблюдаемое поведение>.
Область: <папки>. Критерии: <что проверить>. Связанная задача второго участника: <ссылка>.
Работай в текущем worktree. Выполни проверки, обнови документы и передай результат на ревью.
```

## Передача на ревью

- Что сделано и зачем, задача и ID правил.
- Проверки: команды, результат, пропуски.
- Изменения контракта, миграции, переменные окружения.
- Оставшиеся ограничения и следующий шаг второго участника.

## Выпуск

- Только по поручению владельца; перед выпуском подготовить версию, миграции, резервирование, проверку здоровья и откат.
- Подготовка production описана в [deploy](../deploy/README.md).
