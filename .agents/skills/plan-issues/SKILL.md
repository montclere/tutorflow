# Plan Issues

Используй при запросе «разбери BR на Issues», а не при обычном кодинге.

1. Прими диапазон/список BR-ID или UC-ID. Загрузи только указанные правила и непосредственно связанные UC; проверь их существование `python3 scripts/check.py spec`.
2. Сгруппируй связанные BR в небольшие **вертикальные** задачи, каждая завершает наблюдаемое поведение. Не дели механически 1 BR = 1 Issue; не объединяй задачи без нужды.
3. Укажи зависимости: какие issues требуют реализованного идентификатора пользователя, карточки, доступа, занятия. Предлагай порядок, не называй независимые задачи зависимыми.
4. Для каждого Issue составь краткий Markdown: цель, BR/UC IDs, ожидаемые положительные и отрицательные исходы, границы задачи, зависимость, доказательство через тесты. Не копируй полный текст BR.
5. Если правило не определяет ключевой результат, **не угадывай**: обозначь строго конкретный blocker и вынеси из текущей готовой очереди. Открытые вопросы не превращай автоматически в рабочие задачи.
6. До создания проверь дубли `gh issue list --search` и существующие PR; затем создай `gh issue create --title ... --body-file ... --label ...` по доступным правам. Если GitHub не авторизован, выдай готовые тексты и команды без заявления, что Issues созданы.
7. Для одного потока работы не генерируй более 5–8 Issues за раз, если не попросили иначе.
8. GitHub Project: добавь созданные issues в Ready/Backlog при доступности CLI; зависимость между issues оформляй штатными GitHub возможностями если они доступны, иначе отметь в тексте.

Вывод: только созданные ссылки, порядок выполнения, blockers; никаких новых planning.md.
