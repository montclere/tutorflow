# backend

Модульный монолит по образцу форума; действуют также [общие правила](../AGENTS.md).

- Смотри карту файлов в [README](README.md); инструкции по запуску и миграциям описаны там же.
- Держи простой модуль плоским, как `app/modules/health`: добавляй файлы схем и адаптеров по необходимости.
- Для инвариантов, переходов состояний, прав и внешних вызовов используй полный модуль, как `app/modules/students`: domain, application, infrastructure, presentation.
- В domain держи сущности, значения и ошибки; меняй состояние через методы сущности.
- В application держи сценарии и Protocol-порты; вызывай БД, время и внешние сервисы через эти порты.
- В infrastructure реализуй порты; возвращай из репозитория доменные объекты, управляй транзакцией через единицу работы.
- В presentation разбирай ввод, проверяй доступ и вызывай сценарий; не помещай туда бизнес-правила.
- Направляй зависимости внутрь: domain не знает остальные слои, application не знает infrastructure и presentation.
- Не импортируй внутренности соседнего модуля; связи выражай контрактами `app/shared/application/contracts`, реализации собирай в `app/composition.py`.
- Не импортируй модули из shared; складывай туда только общее ядро, не бизнес-логику конкретного модуля.
- Держи модели и метаданные в своём модуле; регистрируй их в `app/persistence.py`, меняй схему только миграциями.
- Подключай роутеры через `app/api_v1.py`, приложение собирай фабрикой в `app/main.py`, конфигурацию читай в одном месте.
- Проверяй права на сервере для каждого объекта; изменения API отражай в [контракте](../docs/api/README.md).
- Тестируй правила без сети, API и БД — интеграционно после их реализации; границы импортов проверяет `tests/test_architecture.py`.
- Добавляй новые слои по мере необходимости.
- Выполняй `./scripts/dev.sh check` из корня; HTTP-тесты используют отдельный PostgreSQL по инструкции README.
