# TutorFlow

## Контекст задачи

- Прочитай этот файл и AGENTS.md по пути к затронутым файлам. Начинай с выбранной области, затем открывай только нужные источники по её указателям.
- Области проекта — [backend](backend/), [frontend](frontend/), [документы](docs/), [развёртывание](deploy/), [сквозные тесты](tests/e2e/), [утилиты](scripts/) и [процедуры агента](.agents/).
- Перед изменением проверь текущую ветку, рабочее дерево и границы задачи. Сохраняй существующие изменения.
- Прочитай связанные Issue, UC и BR. Открывай соседние модули при изменении их контрактов или наличии конкретной зависимости.
- Продуктовые неоднозначности согласуй до зависимой реализации. Остальную работу продолжай в пределах поручения.

## Общие правила кода

- Держи бизнес-решения в доменном ядре модульного монолита. Соблюдай владение данными и публичные границы модулей.
- Используй понятные общепринятые имена, явные типы и контракты. Имена операций должны объяснять результат, включая возможность отсутствия объекта.
- Упрощай условия, сокращай вложенность, удаляй лишние действия и переиспользуй подходящий код. Большие функции разбивай на понятные шаги, мелкие обёртки объединяй, когда это проясняет сценарий.
- Секреты, параметры окружения и настраиваемые ограничения передавай через конфигурацию. Фиксированные значимые значения оформляй константами.
- Идентификаторы пиши по-английски, документы и сообщения человеку — по-русски.
- Проверяй наблюдаемый результат, права, границы и применимые повторы или гонки. Сохраняй ID правил и смысл требований.

## Скрипты и процедуры

- Сначала изучи справку существующих [скриптов](scripts/) и используй готовую команду проверки, форматирования или генерации.
- Если проверки не хватает, расширь подходящий скрипт и его тесты. Новый самостоятельный инструмент добавляй при отдельной ответственности, которую неудобно выразить существующими режимами.
- Разовая команда допустима для диагностики конкретного сбоя. Повторяемую проверку закрепи в штатном инструменте.
- Применяй одну подходящую процедуру из [.agents](.agents/) по задаче. Порядок работы хранится в скиллах, механические проверки выполняют скрипты.
- Выполняй адресные проверки. Повторяй их после изменений или отказов. Полный прогон требуется при сдаче законченного потока в CI.
- Показывай реально выполненные проверки, ошибки, оставшуюся работу и пути к логам.

## Git и GitHub

- Один UC или самостоятельная техническая работа — одна ветка от dev и один PR. Работай в текущей ветке, когда так поручил владелец.
- Имена рабочих веток — action/uc-NNN для UC и action/area/issue-N для остальных задач. Свободное описание в имя не добавляй. Префикс codex/ запрещён.
- Действия и области выбирай из единого словаря в конфигурации [утилит](scripts/). Команда check git-policy выводит допустимые значения; github branch генерирует имя, check branch-name проверяет его. Переходные исключения привязаны к конкретному открытому PR и удаляются после его слияния.
- Один коммит содержит законченную осмысленную часть работы. Самостоятельно проверяемые задачи обычно разделяются на коммиты.
- Формат сообщения — действие(область): краткое описание (Issue #номер). Действие и область пиши по-английски строчными буквами, описание и пояснения — по-русски. Пример — add(identity): регистрация преподавателя (Issue #6). Для нескольких задач указывай каждый Issue явно.
- Заголовок PR для UC — UC-NNN: название сценария; для технической работы — краткая цель задачи. В PR указывай родительский Issue UC или самостоятельную техническую задачу. Подзадачи и зависимости связывай штатными средствами GitHub.
- Выполняй Git/GitHub-действия в пределах поручения. Merge и изменения реальных окружений требуют явного поручения.
- Сливай через merge-коммит с заголовком Merge PR #номер: краткое русское описание. В теле оставляй пустую строку после заголовка и полный URL этого же PR. Сообщение генерируй режимом github merge. Сохраняй отдельные законченные коммиты.
- Секреты и локальные артефакты исключай из коммита. Проверки должны проходить без отключения защит.
