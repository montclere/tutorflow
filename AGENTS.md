## Источники истины
- `docs/business-rules.md` — нормативное поведение; ID `BR-XXX` неизменны.
- `docs/use-cases.md` — контекст и сквозные пользовательские сценарии; не дублируй в issues.
- `docs/product.md` — цели и UX-принципы, не источник новых бизнес-требований.
- Issue — конкретный ограниченный объём работы и проверяемые критерии.
- Код и тесты — реализация; не изменяй продуктовые требования ради проходящего теста.

## Обязательный цикл
1. Планирование бэклога: `.agents/skills/plan-issues/SKILL.md`.
2. Разработка Issue: `.agents/skills/implement-issue/SKILL.md`.
3. Финальное ревью PR: `.agents/skills/review-pr/SKILL.md`.
Skills вызываются по задаче; не читай их все в каждом рабочем цикле.

## Экономия времени и токенов
- По умолчанию читай только Issue, указанные BR-ID, связанные UC и затронутый код; не загружай все документы в контекст.
- Не запускай полный набор тестов локально после каждого файла. Целевые: `python3 scripts/check.py rule BR-005 [BR-...]`.
- Сначала проектируй тест-кейсы, затем один RED-прогон новых тестов, затем реализация и один целевой GREEN-прогон; повторять только при ошибках.
- Перед PR — `python3 scripts/check.py pr`; полная регрессия — в GitHub Actions.
- Не печатай огромные успешные логи; показывай краткий итог. При ошибке — релевантный хвост и путь к полному логу.
- Не запускай несколько независимых AI-ревью одного маленького изменения: одно содержательное ревью перед PR.
- Не добавляй файлы, слои, зависимости, паттерны и абстракции «на будущее» без текущей потребности.

## Бизнес-ограничения
- Первый этап: один аккаунт — одна роль; карточка ученика существует без аккаунта.
- Модульный монолит; границы: Identity, Students, Scheduling. Внутренние модули, не сетевые сервисы.
- Изоляция данных преподавателей — обязательная проверка.
- Не придумывай политику детских аккаунтов, правовую модель и финансовые правила, если BR недостаточно точен; помечай Issue blocked.
- Не выдавай автоматический переход времени за доказательство фактического проведения занятия.
- Подтверждение пользователя требуется для новых бизнес-решений, изменения продукта, секретов, платёжной инфраструктуры и merge.

## Git/GitHub
- Issue ссылается на BR-ID; PR связан с Issue; тесты ссылаются на BR-ID.
- Перед коммитом проверяй `git diff`; не коммить секреты, `.env`, логи и артефакты.
- Не закрывай Issue до успешного CI и merge. Не сливай PR самостоятельно без разрешения владельца.
- Не используй `--no-verify` и не отключай проверки ради успеха.
